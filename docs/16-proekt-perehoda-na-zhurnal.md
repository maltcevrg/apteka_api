# Проект: журнал операций как единственный источник баланса

Предложение отказаться от таблицы `bonus_balances` и хранить остаток прямо в журнале `card_operations` — колонкой «остаток после операции». Статус: **решение принято — делать, до отчётов**. Ответы на открытые вопросы — в разделе 8. **API ещё не в бою, база пустая**, поэтому разделы о миграции данных (4) и переходном VIEW (2.3) не применяются — см. [docs/17](17-plan-perehoda-na-zhurnal.md).

## 1. Суть

Сейчас баланс живёт в двух местах: журнал `card_operations` (что было) и `bonus_balances` (сколько сейчас). Они пишутся одной транзакцией, но это два хранилища, и их всегда нужно сверять.

Предлагается: журнал становится единственным. Каждая строка знает остаток **после себя** — по кошельку (карта + юрлицо) и по карте целиком. Текущий баланс — это последняя строка. Отмена чека — не пометка на старой строке, а **новая строка со знаком минус** (сторно). Таблица `bonus_balances` удаляется.

Принятые вводные (от заказчика):

- старая история переписывается: у каждой операции должно быть юрлицо;
- у старых переносов без юрлица юрлицо берётся по владельцу карты (ИНН-владелец карты);
- отмена чека — новой строкой.

## 2. Целевая модель данных

### 2.1. `card_operations` (меняется)

| Поле | Было | Станет |
|:--|:--|:--|
| `legal_entity_id` | NULL допустим | заполняется всегда; NULL остаётся только у старых переносов карт, у которых вообще нет операций с юрлицом (решение заказчика) |
| `pharmacy_id` | NULL у переносов | без изменений |
| `action` | 0–4 | добавляется **5 — отмена (сторно)** |
| `amount` | со знаком | без изменений; у сторно — сумма исходной с обратным знаком |
| `wallet_after` | — | **новое**: остаток кошелька (эта карта + это юрлицо) после операции |
| `card_after` | — | **новое**: остаток карты целиком после операции |
| `parent_id` | — | **новое**: для сторно — id отменённой операции; для исходной — NULL |
| `deleted_at` | = отмена | **остаётся как пометка «отменена»** на исходной строке, чтобы не отменить дважды и чтобы старые выборки `whereNull('deleted_at')` продолжили работать. Семантически — «погашена». |

Индексы: `(card_id, id)` — последняя строка по карте; `(card_id, legal_entity_id, id)` — последняя строка по кошельку; `parent_id` уникальный (одну операцию можно сторнировать один раз).

### 2.2. `cards` (дополняется)

| Поле | Зачем |
|:--|:--|
| `legal_entity_id` | **ИНН-владелец карты.** Нужен для переписывания старых переносов и как юрлицо по умолчанию, если понадобится. Заполняется по первой операции карты. |

### 2.3. `bonus_balances` — удаляется

После миграции и сверки. На переходный период можно оставить как **представление** (VIEW) с тем же именем и полями, чтобы любые внешние запросы (phpMyAdmin, выгрузки) не сломались:

```sql
CREATE VIEW bonus_balances AS
SELECT o.card_id, o.legal_entity_id, o.wallet_after AS sum
FROM card_operations o
JOIN (SELECT card_id, legal_entity_id, MAX(id) AS id
      FROM card_operations GROUP BY card_id, legal_entity_id) last ON last.id = o.id;
```

## 3. Алгоритмы

Все операции по-прежнему в транзакции с блокировкой строки карты (`SELECT … FOR UPDATE` в `cards`) — таблица `cards` остаётся, блокировать есть что.

### 3.1. Баланс

```sql
-- карта целиком
SELECT card_after FROM card_operations WHERE card_id = ? ORDER BY id DESC LIMIT 1;

-- по кошелькам (для отчётов и переноса)
SELECT o.legal_entity_id, o.wallet_after
FROM card_operations o
JOIN (SELECT legal_entity_id, MAX(id) id FROM card_operations WHERE card_id = ? GROUP BY legal_entity_id) l ON l.id = o.id;
```

Если строк нет — баланс 0. Оба запроса идут по индексу и не зависят от длины истории.

### 3.2. Начисление, списание, возвраты

1. Заблокировать карту.
2. Прочитать `card_after` последней строки карты и `wallet_after` последней строки кошелька (карта + ИНН из запроса).
3. Проверить `card_after + amount ≥ 0` (правило прежнее: минус не допускается по карте целиком, отдельный кошелёк может уйти в минус).
4. Вставить строку: `wallet_after = prev_wallet + amount`, `card_after = prev_card + amount`.

### 3.3. Отмена чека (`/increase/cancel`, `/decrease/cancel`)

1. Заблокировать карту.
2. Найти исходную операцию по карте + номеру + типу документа **с `deleted_at IS NULL` и без сторно** (`parent_id` не занят).
3. Проверить `card_after − amount_исходной ≥ 0`.
4. Вставить строку: `action = 5`, `parent_id = исходная.id`, `amount = −исходная.amount`, `legal_entity_id`, `pharmacy_id` — из исходной, `document_number`/`document_type` — из исходной, **`document_date` = сегодня**, `wallet_after`/`card_after` — пересчитаны от последних.
5. Поставить `deleted_at` на исходной (пометка «погашена»).

Повторная отмена того же чека → 404/409, как и сейчас.

### 3.4. Перенос баланса

По каждому кошельку источника с ненулевым `wallet_after`: две строки `action = 2` (минус на источнике, плюс на приёмнике) с тем же юрлицом. Уже так работает; меняется только то, что остаток пишется в строки, а не в `bonus_balances`.

### 3.5. Чеки задним числом

Нарастающий итог считается **по порядку записи (`id`)**, а не по дате документа. Иначе вставка чека «за вчера» требовала бы пересчёта всех последующих строк. Следствие: в выписке, отсортированной по дате документа, колонка «остаток после» может выглядеть непоследовательно у задним-числовых чеков. В выписке это решается сортировкой по `id` (порядок проведения) с отдельной колонкой «дата документа» — так делают банки.

## 4. Миграция данных

Одноразовый скрипт (artisan-команда), выполняется один раз на проде при остановленном API (`artisan down`, несколько минут при миллионах строк).

1. Добавить колонки `wallet_after`, `card_after`, `parent_id`, `cards.legal_entity_id`; `action 5`.
2. **Юрлицо карты:** `cards.legal_entity_id` = юрлицо первой операции карты (по `id`), у которой оно есть. Карты без операций — NULL, это нормально.
3. **Старые переносы без юрлица:** `legal_entity_id` = `cards.legal_entity_id` той карты, к которой относится строка. Если и у карты нет — юрлицо по умолчанию (одно, задаётся параметром команды) — команда печатает, сколько таких строк.
4. **Отмены → сторно:** для каждой строки с `deleted_at IS NOT NULL` вставить строку `action = 5`, `parent_id`, `amount = −amount`, `document_date = DATE(deleted_at)`, `created_at = deleted_at`. Строки вставляются с новыми `id`, поэтому для корректного порядка нарастающего итога шаг 5 сортирует по `created_at, id`, а не только по `id`. (Только при миграции; дальше `id` и время растут вместе.)
5. **Нарастающий итог:** одним проходом по каждой карте в порядке `created_at, id` заполнить `wallet_after` и `card_after`.
6. **Сверка:** для каждой карты `card_after` последней строки = `SUM(sum)` в `bonus_balances`; по кошелькам — то же. Команда печатает расхождения. **Пока есть расхождения — `bonus_balances` не удаляется**, разбираем вручную.
7. `bonus_balances` → VIEW (или удалить).

Откат: резервная копия базы перед запуском; код предыдущей версии. Скрипт идемпотентен по шагам 2–5 (можно перезапустить).

## 5. Что меняется в коде

Для касс и 1С **внешний API не меняется**: те же маршруты, те же ответы (плюс, при желании, новое поле).

## 6. Плюсы

1. **Один источник правды.** Расхождение «журнал ≠ остаток» невозможно по построению; сверки «журнал против `bonus_balances`» больше не нужны.
2. **Полная история остатков.** Остаток карты на любой момент — одна строка; выписка с колонкой «остаток после» — бесплатно. Разбор претензии клиента («у меня было 500, куда делись») — по одной выборке.
3. **Отмена — видимое событие.** Сейчас отмена «исчезает» в `deleted_at`, её дата живёт в служебном поле. Станет обычной строкой с датой, суммой и ссылкой на исходный чек. Это соответствует бухгалтерской практике (сторно) и упрощает отчёты по месяцам.
4. **У каждой операции есть юрлицо** (кроме редких старых переносов, см. 8.1). Срез по ИНН сходится по построению.
5. **Меньше кода и таблиц.** Минус `BonusBalanceService`, модель, фабрика.
6. **Скорость не хуже.** Баланс — один индексированный запрос `ORDER BY id DESC LIMIT 1`; запись — одна вставка вместо вставки + обновления.

## 7. Минусы и риски

1. **Переписывание ядра.** Затрагивается всё, что касается денег: операции, отмена, перенос, тесты. Плюс миграция данных. Любая ошибка — в деньгах.
2. **Одноразовая миграция на живых данных** с остановкой API. Нужны резервная копия, прогон на копии базы, сверка. Это самая рискованная часть; код после неё — обычная работа.
3. **Искусственное юрлицо у старых переносов.** «Юрлицо по владельцу карты» — допущение; для старых переносов между картами разных ИНН обороты по юрлицам за прошлые месяцы будут приближёнными. Сальдо по картам точным останется. Нужно зафиксировать в документации, с какой даты данные по ИНН точные.
4. **Нарастающий итог нельзя «подправить».** Если когда-нибудь понадобится исправить сумму старой операции, пересчитывать придётся все последующие строки карты. Сейчас достаточно поправить одну строку и один кошелёк. Решается правилом «только сторно + новая операция, старые строки не редактируем» — это и есть правильная практика, но её надо соблюдать.
5. **Нельзя удалять строки журнала.** Очистка/архивация старой истории становится сложнее: удалить строки можно только целиком до некоторой даты, оставив на границе «якорную» строку с остатком. Для 5+ лет хранения это не проблема, но помнить нужно.
6. **Дублирование остатка в каждой строке.** Два `decimal` на строку — около 10 байт; при 7 млн операций в год это ~70 МБ в год сверх текущих 2,2 ГБ. Несущественно.
7. **Параллельность завязана на блокировку карты.** Так уже есть; но если её когда-нибудь уберут, нарастающий итог сломается тихо (две строки прочитают один и тот же «предыдущий» остаток). Защита: уникальный индекс не поможет, нужна дисциплина или проверка `card_after` предыдущей строки в тесте на гонки.
8. **`deleted_at` меняет смысл** с «удалена» на «погашена сторно». Это надо чётко проговорить в документации, иначе следующий разработчик решит, что строки с `deleted_at` можно игнорировать — а они входят в нарастающий итог.

## 8. Решения по открытым вопросам

1. **Юрлицо для старых переносов карт без операций с юрлицом — NULL.** `legal_entity_id` остаётся nullable; таких строк единицы, в отчётах по юрлицам они идут строкой с пустым ИНН. Шаг 7 миграции («NOT NULL») отменяется.
2. **Отмена переноса не нужна.** API её не предусматривает, сторно только для начислений/списаний/возвратов.
3. **`balance_after` в ответе кассам — да.** Поле добавляется в ответ на начисление, списание, возврат и отмену; необязательное, обратную совместимость не ломает.
4. **Делать до отчётов.** Отчёты проектируются сразу под журнал с нарастающим итогом.
