# Алгоритмы операций с бонусами

Документ описывает, что именно делает API при каждой операции с картой и балансом: какие проверки выполняются, в каком порядке, что пишется в базу и какой ответ получает клиент. Алгоритмы соответствуют коду в `packages/Solt/Bonus/src/Services/` и `Http/Requests/`.

## 1. Модель данных

Баланс карты **не хранится одним числом**. Он складывается из нескольких остатков — по одному на каждое юридическое лицо, чьи аптеки начисляли бонусы на эту карту.

| Таблица | Назначение |
|:--|:--|
| `cards` | Карты. Поле `status`: `0` — активна, `1` — заблокирована. Удаление мягкое (`deleted_at`). |
| `bonus_balances` | Остатки: одна строка на пару (карта, юрлицо), поле `sum`. |
| `card_operations` | Журнал: одна строка на каждое движение. Хранит карту, юрлицо, аптеку, реквизиты документа (`document_number`, `document_type`, `document_date`), `amount` со знаком и код `action`. |

Коды `action`:

| Код | Операция | Знак `amount` |
|:--|:--|:--|
| 0 | Начисление | `+` |
| 1 | Списание | `−` |
| 2 | Перенос баланса между картами | `+` на карте-получателе, `−` на карте-источнике |
| 3 | Возврат начисления (покупатель вернул товар, по которому начисляли) | `−` |
| 4 | Возврат списания (покупатель вернул товар, который оплачивал бонусами) | `+` |

**Инварианты**, которые поддерживает система:

1. Баланс карты = `SUM(bonus_balances.sum)` по всем неудалённым строкам карты.
2. Баланс карты = `SUM(card_operations.amount)` по всем неудалённым операциям карты. Оба способа должны давать одно число.
3. Баланс карты никогда не становится отрицательным.
4. Один `document_number` встречается среди активных операций не более одного раза (для переноса — по одному разу на каждой из двух карт).

## 2. Общие шаги для всех запросов

Каждый запрос к `/api/v1/*` проходит одинаковую подготовку, ниже она не повторяется.

```
1. Проверить заголовок Authorization: Bearer <token>.
   Токен недействителен или отсутствует → 401 {"message": "Unauthenticated."}
2. Проверить тело запроса по правилам валидации операции.
   Ошибка → 422 {"message": "...", "errors": {поле: [тексты]}}
   Ничего в базу не пишется.
3. Нормализовать дату документа к формату Y-m-d H:i:s.
4. Выполнить алгоритм операции (разделы ниже).
```

**Активная карта.** Во всех операциях карта ищется по `short_code` при условии `deleted_at IS NULL` и `status = 0`. Заблокированная или удалённая карта считается не найденной.

**Ответ 202.** API использует код `202 Accepted` с полем `message` для бизнес-отказов: «карта не найдена», «недостаточно бонусов», «операцию нельзя отменить». Это не ошибка сервера и не ошибка валидации; клиент должен прочитать `message`.

## 3. Получение баланса

`GET /api/v1/bonus/balance/{short_code}`

```
1. Найти активную карту по short_code.
   Нет → 202 {"message": "Карта не найдена"}
2. balance = SUM(sum) по строкам bonus_balances этой карты (deleted_at IS NULL).
   Если строк нет — 0.
3. Округлить до 2 знаков.
4. → 200 {"balance": balance}
```

Операция только читает данные, ничего не блокирует и не пишет.

## 4. Начисление

`POST /api/v1/bonus/increase`

Входные данные: `short_code`, `pharmacy_number`, `inn`, `document_date`, `document_number`, `document_type`, `amount`.

Валидация: карта с таким `short_code` существует; аптека с таким `pharmacy_number` (1–99) существует; юрлицо с таким `inn` (10–20 цифр) существует; `document_number` не длиннее 12 символов и **не встречается среди активных операций**; `amount ≥ 0.01`.

```
НАЧАТЬ ТРАНЗАКЦИЮ
  1. Найти активную карту по short_code и ЗАБЛОКИРОВАТЬ её строку
     (SELECT ... FOR UPDATE). Пока транзакция не завершится, другие
     операции с этой картой ждут.
  2. balance = текущий баланс карты (свежий запрос, под блокировкой).
  3. Если balance + amount < 0 → ОТКАТ, 202 {"message": "Нулевой баланс"}.
     (Для начисления amount > 0, поэтому условие не срабатывает;
      проверка общая для всех операций движения.)
  4. Записать в card_operations строку:
       action = 0, amount = +amount, карта, юрлицо по inn,
       аптека по pharmacy_number, реквизиты документа.
  5. Изменить остаток по паре (карта, юрлицо):
       a. Найти строку bonus_balances для карты и юрлица
          (с блокировкой FOR UPDATE).
       b. Нет строки → создать с sum = amount.
       c. Есть → sum = sum + amount.
ЗАФИКСИРОВАТЬ
→ 201, тело — созданная операция
```

Любая ошибка внутри транзакции (сбой базы, нарушение ограничений) откатывает и запись операции, и изменение остатка, а клиент получает `500`. Частичного состояния «операция есть, остаток не изменён» быть не может.

## 5. Списание

`POST /api/v1/bonus/decrease`

Те же входные данные, что у начисления. Отличие валидации: `amount ≤ −0.01` — **сумма передаётся отрицательной**.

```
НАЧАТЬ ТРАНЗАКЦИЮ
  1. Найти активную карту, заблокировать строку.
  2. balance = текущий баланс карты.
  3. Если balance + amount < 0 (то есть |amount| > balance)
     → ОТКАТ, 202 {"message": "Нулевой баланс"}.
     Баланс не меняется, операция не записывается.
  4. Записать в card_operations: action = 1, amount = −|amount|.
  5. Изменить остаток по паре (карта, юрлицо-списатель):
       нет строки → создать с sum = amount (отрицательное);
       есть → sum = sum + amount.
ЗАФИКСИРОВАТЬ
→ 201
```

**Важно про шаг 5.** Проверяется общий баланс карты (шаг 3), а списание вычитается из остатка конкретного юрлица, которое указано в запросе. Если бонусы начислило юрлицо А, а списывает юрлицо Б, остаток А останется прежним, а остаток Б уйдёт в минус. Общий баланс при этом корректен и неотрицателен. Остатки по юрлицам нужны для взаиморасчётов между ними: отрицательный остаток Б означает, что Б «отоварило» бонусы, начисленные А.

Благодаря блокировке на шаге 1 два одновременных списания с одной карты выполняются строго по очереди: второе увидит баланс уже после первого и получит отказ, если бонусов не хватает.

## 6. Возвраты

Возврат — это операция, обратная начислению или списанию, когда покупатель вернул товар. В отличие от отмены (раздел 7) возврат **не удаляет исходную операцию**, а добавляет новую с противоположным знаком и собственным номером документа (чек возврата).

### 6.1. Возврат начисления

`POST /api/v1/bonus/increase/return` — покупатель вернул товар, за который ему начислили бонусы; начисленное нужно забрать.

Валидация как у списания: `amount ≤ −0.01`. Алгоритм полностью совпадает с разделом 5, кроме `action = 3`. В частности, действует проверка баланса: если покупатель уже потратил начисленные бонусы и забрать нечего → `202 «Нулевой баланс»`.

### 6.2. Возврат списания

`POST /api/v1/bonus/decrease/return` — покупатель вернул товар, который оплачивал бонусами; списанное нужно вернуть на карту.

Валидация как у начисления: `amount ≥ 0.01`. Алгоритм совпадает с разделом 4, кроме `action = 4`.

## 7. Отмена операции (корректировка)

`POST /api/v1/bonus/increase/cancel` и `POST /api/v1/bonus/decrease/cancel` — один и тот же обработчик.

Отмена нужна для исправления ошибки: чек пробит неверно и его аннулируют. Операция **удаляется из журнала** (мягко, через `deleted_at`), и её влияние на остаток снимается. После отмены `document_number` снова свободен и может быть использован.

Входные данные: `short_code`, `document_date`, `document_number`, `document_type`.

Валидация: карта существует; операция с таким `document_number` существует.

```
НАЧАТЬ ТРАНЗАКЦИЮ
  1. Найти активную карту, заблокировать строку.
     Нет → ОТКАТ, 202 {"message": "Не удалось отменить операцию"}
  2. Найти активную операцию по тройке
     (short_code, document_number, document_type).
     Нет → ОТКАТ, 202 «Не удалось отменить операцию»
     (в том числе если операция уже отменена ранее — повторная
      отмена безопасна и ничего не меняет).
  3. balance = текущий баланс карты.
  4. Если balance − operation.amount < 0 → ОТКАТ, 202 «Не удалось отменить операцию».
     Это срабатывает при отмене НАЧИСЛЕНИЯ, если покупатель уже
     потратил начисленные бонусы: отмена увела бы баланс в минус.
     Отмена списания (amount < 0) всегда проходит эту проверку.
  5. Изменить остаток по паре (карта, юрлицо операции):
       sum = sum − operation.amount.
  6. Пометить операцию удалённой (deleted_at = now).
ЗАФИКСИРОВАТЬ
→ 204 (без тела)
```

Поля `document_date` и `pharmacy_number` при поиске операции не участвуют: операция определяется картой, номером и типом документа.

## 8. Перенос баланса между картами

`POST /api/v1/bonus/move` — например, при замене утерянной карты на новую.

Входные данные: `short_code_from`, `short_code_to`, `document_date`, `document_number`, `document_type`.

Валидация: обе карты существуют; `document_number` свободен.

```
НАЧАТЬ ТРАНЗАКЦИЮ
  1. Найти активную карту-источник, заблокировать.
  2. Найти активную карту-получатель, заблокировать.
  3. balance_from = баланс карты-источника.
  4. Если balance_from == 0 → ОТКАТ, 202 {"message": "Ошибка переноса баланса"}.
  5. Записать операцию на карте-получателе:
       action = 2, amount = +balance_from, документ из запроса.
  6. Записать операцию на карте-источнике:
       action = 2, amount = −balance_from, тот же документ.
  7. Для КАЖДОЙ строки bonus_balances карты-источника (по каждому юрлицу):
       a. На карте-получателе остаток этого юрлица += sum
          (создать строку, если её нет).
       b. На карте-источнике остаток этого юрлица −= sum (становится 0).
ЗАФИКСИРОВАТЬ
→ 200 {"message": "Баланс успешно перенесен"}
```

Переносится **вся сумма целиком, с сохранением разбивки по юрлицам**: взаиморасчёты между юрлицами после переноса не меняются. Частичный перенос не предусмотрен. Операции переноса не привязаны к юрлицу и аптеке (`legal_entity_id`, `pharmacy_id` = NULL). Карта-источник после переноса остаётся активной с нулевым балансом; заблокировать её — отдельный запрос `DELETE /bonus/card/{short_code}`.

## 9. Операции с карточкой клиента

Эти операции не трогают баланс.

### 9.1. Создание карты — `POST /bonus/card`

```
1. Валидация: short_code (9–13 символов) уникален среди неудалённых карт;
   phone (формат +7XXXXXXXXXX) уникален среди неудалённых карт;
   обязательны firstname, name, birthdate, gender (0/1),
   newsletter_agree (0/1), status (0–2).
2. Записать строку в cards.
→ 201, тело — карта. Баланс новой карты — 0 (строк в bonus_balances нет).
```

### 9.2. Получение карты — `GET /bonus/card/{short_code}`

```
1. Найти активную карту. Нет → 202 «Карта не найдена».
→ 200, тело — карта.
```

### 9.3. Поиск по телефону — `POST /bonus/find` с `{"phone": "+7..."}`

```
1. Валидация: телефон в формате +7XXXXXXXXXX и есть в cards.
2. Найти активную карту с этим телефоном. Нет → 202 «Карта не найдена».
→ 200, тело — карта.
```

### 9.4. Изменение карты — `PUT /bonus/card/{short_code}`

```
1. Найти активную карту. Нет → 202.
2. Перезаписать переданные поля (short_code не меняется).
→ 200
```

### 9.5. Блокировка карты — `DELETE /bonus/card/{short_code}`

```
1. Найти активную карту. Нет → 202 «Не удалось удалить карту».
2. status = 1, deleted_at = now.
→ 204
```

Остатки и операции карты сохраняются в базе, но карта перестаёт находиться во всех операциях: баланс по ней не выдаётся, начисления и списания невозможны. Восстановление через API не предусмотрено.

## 10. Сводная таблица

| Операция | Проверка баланса | Что пишется | Успех | Отказ |
|:--|:--|:--|:--|:--|
| Баланс | — | ничего | 200 `balance` | 202 |
| Начисление | формально | +операция (0), остаток += | 201 | 202 |
| Списание | `balance ≥ \|amount\|` | +операция (1), остаток −= | 201 | 202 |
| Возврат начисления | `balance ≥ \|amount\|` | +операция (3), остаток −= | 201 | 202 |
| Возврат списания | формально | +операция (4), остаток += | 201 | 202 |
| Отмена | `balance − op.amount ≥ 0` | операция → удалена, остаток −= op.amount | 204 | 202 |
| Перенос | `balance_from ≠ 0` | +2 операции (2), остатки перенесены по юрлицам | 200 | 202 |

Все операции, которые пишут в базу, выполняются в одной транзакции с блокировкой строки карты. Ошибка на любом шаге откатывает всё целиком.

## 11. Известные особенности

1. **Заблокированная карта проходит валидацию.** Правило `exists:cards,short_code` не смотрит на `status` и `deleted_at`. Для операций баланса и карточки это даёт корректный `202 «Карта не найдена»`, но для начисления, списания, возвратов и переноса карта ищется уже внутри транзакции и при `null` код упадёт с `500`. Клиенту стоит перед операциями проверять карту через `GET /bonus/card/{short_code}`; на стороне API это место стоит закрыть явной проверкой.
2. **Типы документов не контролируются.** `document_type` — произвольная строка до 40 символов. Отмена ищет операцию по точному совпадению типа, поэтому касса должна передавать при отмене тот же тип, что при создании.
3. **Уникальность `document_number` глобальная**, а не в рамках аптеки или юрлица. Если две аптеки используют одинаковую нумерацию чеков, вторая получит `422`. Кассе следует включать в номер префикс аптеки.
4. **Дата документа при отмене не проверяется**, хотя и обязательна в запросе.
