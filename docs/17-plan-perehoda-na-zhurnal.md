# План перехода на журнал с нарастающим итогом

Реализация проекта из [docs/16](16-proekt-perehoda-na-zhurnal.md). **API ещё не в боевой эксплуатации, база пустая** — поэтому переносить историю, сверять с `bonus_balances` и планировать простой не нужно. Делаем сразу целевую модель, одним PR. **Статус: реализовано.** Отличия от плана: в ответе на отмену `balance_after` нет (ответ `204` без тела, как раньше, чтобы не менять контракт для 1С); `migrate:fresh` вызывается из `obnovlenie.php?…&fresh=1`.

## 1. Что делаем

### 1.1. Схема (новые миграции)

`card_operations`:

| Колонка | Тип | Примечание |
|:--|:--|:--|
| `wallet_after` | decimal(12,2) NOT NULL | остаток кошелька (карта + юрлицо) после операции |
| `card_after` | decimal(12,2) NOT NULL | остаток карты после операции |
| `parent_id` | bigint NULL, FK → card_operations, UNIQUE | у сторно — id отменённой операции |
| `amount` | decimal(8,2) → decimal(12,2) | заодно расширяем |

Индексы: `(card_id, id)`, `(card_id, legal_entity_id, id)`. `legal_entity_id` остаётся nullable (решение заказчика для будущих крайних случаев; в новой логике заполняется всегда).

`cards`: `legal_entity_id` bigint NULL, FK → legal_entities — ИНН-владелец карты, заполняется первой операцией карты.

`bonus_balances`: удаляется (`dropIfExists`). VIEW не нужен — внешних потребителей таблицы нет.

`action`: добавляется значение **5 — отмена (сторно)**.

### 1.2. Код

| Компонент | Что делаем |
|:--|:--|
| `LedgerService` (новый) | единственная точка записи: под блокировкой карты читает последние `card_after` / `wallet_after`, пишет строку с итогами, при первой операции карты заполняет `cards.legal_entity_id` |
| `CardOperationService::store` | проверка `card_after + amount ≥ 0` → `LedgerService::append` |
| `CardOperationService::delete` (отмена) | найти исходную (`deleted_at IS NULL`, без потомка) → проверка баланса → `append(action 5, parent_id)` → `deleted_at` на исходной |
| `CardOperationService::move` | по кошелькам источника (последняя строка каждого юрлица) — пары `append` с тем же юрлицом |
| `Card::getBalance()` | `card_after` последней строки, 0 если строк нет |
| `Card::wallets()` (новый) | последняя строка каждого кошелька |
| `CardOperationResource` | + `balance_after` в ответах на начисление, списание, возврат, отмену |
| `BonusBalanceService`, `BonusBalance`, фабрика, интерфейс, ресурс | удаляются |
| `bonus:ledger-check` (новая команда) | проверка цепочки: `card_after[i] = card_after[i−1] + amount[i]` по карте и по кошелькам; доступна через `obnovlenie.php?key=…&check=1` |

Гонки: блокировка строки `cards` (`FOR UPDATE`) сохраняется, чтение последней строки — под ней.

### 1.3. Тесты

- Существующие Feature-тесты проходят; ответы прежние плюс поле `balance_after`.
- Новые: остаток после каждой операции; сторно создаёт строку и помечает исходную; повторная отмена → ошибка; отмена при недостатке баланса → ошибка; перенос по кошелькам; баланс карты без операций = 0; чек задним числом не ломает цепочку; `ledger-check` находит искусственно сломанную цепочку; `cards.legal_entity_id` заполняется первой операцией.

## 2. Выкладка на хостинг

База пустая, поэтому проще всего пересоздать её целиком:

1. Загрузить код из `main`.
2. `obnovlenie.php?key=…&fresh=1` → `migrate:fresh --force` (удаляет все таблицы и создаёт заново), затем `passport:keys` при отсутствии и пересборка кэшей. **Клиент Passport (`client_id`/`secret`) придётся создать заново** — `passport:client --client` тоже вызывается из скрипта, вывод с новым секретом показывается один раз. Записать его в 1С.
3. Проверить: `GET /api/v1/check` → `Unauthenticated`; с токеном — начисление, баланс, отмена, перенос.

Параметр `fresh` в `obnovlenie.php` работает **только если в `.env` стоит `APP_ENV` ≠ `production` или в таблицах нет ни одной операции** — защита от случайного запуска на боевых данных.
