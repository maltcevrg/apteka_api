# План перехода на журнал с нарастающим итогом

Пошаговый план реализации проекта из [docs/16](16-proekt-perehoda-na-zhurnal.md). Что делаем, в каком порядке, как проверяем каждый шаг и как откатываемся.

## 0. Принципы

1. **Сначала данные, потом код.** Новые колонки и перенос истории выкатываются отдельно и работают рядом со старой логикой. Пока они не сверены — ничего не переключаем.
2. **Каждый шаг обратим**, пока не удалена `bonus_balances`. Удаляем её последней, когда всё остальное уже работает на проде.
3. **Внешний API не меняется.** Кассы и 1С ничего не замечают, кроме нового необязательного поля `balance_after`.
4. **Проверка — на копии прод-базы** до выкладки. Без PHP в песочнице это делается CI (тесты на синтетике) + прогон команды переноса на проде в «сухом» режиме (только считает и сверяет, ничего не пишет).

## 2. Этап A — схема и перенос истории

### 2.1. Миграция схемы (`2026_12_01_000001_add_ledger_columns`)

`card_operations`:

| Колонка | Тип | Примечание |
|:--|:--|:--|
| `wallet_after` | decimal(12,2) NULL | NULL = ещё не рассчитано |
| `card_after` | decimal(12,2) NULL | |
| `parent_id` | bigint NULL, FK → card_operations, UNIQUE | ссылка сторно → исходная |

Индексы: `(card_id, id)`, `(card_id, legal_entity_id, id)`.

`cards`: `legal_entity_id` bigint NULL, FK → legal_entities.

Старая логика эти колонки не трогает, NULL ей не мешает.

### 2.2. Команда `bonus:ledger-migrate`

```
php artisan bonus:ledger-migrate --dry-run     # только посчитать и сверить, ничего не писать
php artisan bonus:ledger-migrate               # записать
php artisan bonus:ledger-migrate --card=7001   # одна карта, для разбора
```

Шаги внутри (каждый идемпотентен — повторный запуск даёт тот же результат):

1. **Юрлицо карты.** `cards.legal_entity_id` = `legal_entity_id` первой (по `id`) операции карты, где оно не NULL. Нет такой — остаётся NULL.
2. **Юрлицо старых переносов.** Строки `action = 2` с `legal_entity_id IS NULL` → `cards.legal_entity_id` своей карты. Если и там NULL — остаётся NULL (решение заказчика). Команда печатает, сколько строк получили юрлицо и сколько остались без.
3. **Отмены → сторно.** Для каждой строки с `deleted_at IS NOT NULL`, у которой ещё нет потомка (`parent_id`), вставить строку: `action = 5`, `parent_id`, `amount = −amount`, `card_id`, `legal_entity_id`, `pharmacy_id`, `document_number`, `document_type` — из исходной; `document_date = DATE(deleted_at)`; `created_at = updated_at = deleted_at`.
4. **Нарастающий итог.** По каждой карте: все строки в порядке `created_at, id` (сторно вставлены позже, но должны встать на момент отмены); бегущая сумма по карте → `card_after`, по каждому юрлицу → `wallet_after`. Пачками по 1 000 карт, в транзакции на пачку.
5. **Сверка.** По каждой карте: `card_after` последней строки vs `SUM(sum)` из `bonus_balances`; по каждому кошельку: `wallet_after` последней строки кошелька vs `sum` кошелька. Печать таблицы расхождений (карта, юрлицо, по журналу, в `bonus_balances`, разница) и итогов: карт всего / сошлось / не сошлось.

Код возврата: 0 — расхождений нет; 1 — есть. В режиме `--dry-run` шаги 1–4 считаются в памяти, в базу не пишется ничего.

### 2.3. Тесты этапа A

- Миграция на пустой базе и на базе с данными (фабрики): переносы без юрлица, отменённые операции, карта с двумя кошельками, карта без операций.
- Итог после миграции совпадает с `bonus_balances` в сценариях из тестов `BonusTest`, `MoveBalancesTest`, `*CancelTest`.
- Идемпотентность: двойной запуск не меняет данные.

### 2.4. Выкладка A

1. Код на сервер, `obnovlenie.php?key=…` (миграция схемы — секунды, колонки NULL без заполнения).
2. `obnovlenie.php?key=…&ledger=dry` — сухой прогон, смотрим расхождения.
3. Если расхождения есть — разбираем каждую карту (`--card=`), правим данные **в `bonus_balances` или журнале руками**, повторяем сухой прогон. API при этом работает.
4. Расхождений 0 → `obnovlenie.php?key=…&ledger=run`. API можно не останавливать: старая логика пишет только `amount` и `bonus_balances`, новые колонки у свежих строк останутся NULL — их досчитает этап B при переключении (см. 3.4).

**Откат A:** не нужен — старая логика не зависит от новых колонок. В крайнем случае `migrate:rollback` на одну миграцию.

## 3. Этап B — переключение логики

### 3.1. Код

| Компонент | Что делаем |
|:--|:--|
| `LedgerService` (новый) | `append(card, legalEntity, pharmacy, action, amount, document…, parent=null)`: под блокировкой карты читает последние `card_after`/`wallet_after`, пишет строку с итогами. Единственная точка записи в журнал. |
| `CardOperationService::store` | проверка `card_after + amount ≥ 0` → `LedgerService::append` |
| `CardOperationService::delete` (отмена) | найти исходную (`deleted_at IS NULL`, без потомка) → проверка `card_after − amount ≥ 0` → `append(action 5, parent)` → `deleted_at` на исходной |
| `CardOperationService::move` | по кошелькам источника (последняя строка каждого) — пары `append` с тем же юрлицом |
| `Card::getBalance()` | `card_after` последней строки, 0 если строк нет |
| `Card::wallets()` (новый) | последняя строка каждого кошелька — для переноса и отчётов |
| `CardOperationResource` | + `balance_after` (= `card_after`) в ответах на начисление/списание/возврат/отмену |
| `BonusBalanceService`, `BonusBalance` | **пока остаются**, но больше не вызываются |
| `bonus:ledger-check` (новая команда) | проверяет цепочку: для каждой карты `card_after[i] = card_after[i−1] + amount[i]`, то же по кошелькам; плюс сравнение с `bonus_balances`, пока она есть. Печатает разрывы. |

Гонки: блокировка строки `cards` (`FOR UPDATE`) остаётся; чтение «последней строки» идёт уже под ней.

### 3.2. Переходный период внутри B

Пока `bonus_balances` существует, `LedgerService::append` **дополнительно обновляет её** (как раньше). Это даёт:
- независимую сверку в `bonus:ledger-check` на живом трафике;
- мгновенный откат на старую логику без потери данных.

Удаляется в этапе C.

### 3.3. Тесты этапа B

- Все существующие Feature-тесты проходят без изменений ответов (кроме нового поля).
- Новые: остаток после каждой операции в строке; сторно создаёт строку и помечает исходную; повторная отмена → ошибка; отмена при недостатке баланса → ошибка; перенос по кошелькам пишет `wallet_after` верно; `getBalance` на карте без операций = 0; чек задним числом не ломает цепочку; `ledger-check` находит искусственно сломанную цепочку.
- Тест на гонку: два параллельных списания — в CI не воспроизводится, проверяем кодом (блокировка до чтения последней строки) и ревью.

### 3.4. Выкладка B

1. Резервная копия базы (ISPmanager → Базы → Экспорт).
2. `obnovlenie.php?key=…&down=1` — режим обслуживания (кассы получают 503, 1С повторит).
3. Код на сервер.
4. `obnovlenie.php?key=…&ledger=run` — досчитать итоги для строк, появившихся после этапа A (команда досчитывает только строки с `card_after IS NULL`, идёт по порядку).
5. `obnovlenie.php?key=…&ledger=check` — цепочка и сверка с `bonus_balances` = 0 расхождений.
6. `obnovlenie.php?key=…&up=1`. Простой — 5–15 минут.
7. В течение 1–2 дней: `ledger=check` раз в день. Смотрим лог на ошибки.

**Откат B:** вернуть код этапа A (файлы), `config:cache`. Данные совместимы: `bonus_balances` велась параллельно, старая логика продолжит с неё. Сторно-строки останутся в журнале — старая логика их не читает (у неё баланс из `bonus_balances`), но они видны в истории; это допустимо.

## 7. Риски плана и что с ними делать

| Риск | Мера |
|:--|:--|
| Расхождения в сухом прогоне A | Это находка, а не проблема плана: разбираем по картам до B. Если их много — отдельно выясняем системную причину. |
| Порядок `created_at, id` при сортировке даёт неверную последовательность для старых строк (одинаковые секунды) | Внутри одной секунды — по `id`; сторно всегда позже исходной по `created_at`. Для текущего баланса порядок внутри секунды не важен — сумма та же. |
| Длительность шага 4 на миллионах строк | Пачками по картам; при 7 млн строк — ориентировочно 10–20 минут на хостинге. Делается в A без простоя. |
| Касса отправила операцию во время выкладки B | Режим обслуживания отдаёт 503; 1С по шаблону из docs/11 повторяет запрос. |
| Забыли `balance_after` в каком-то ответе | Тесты на все четыре маршрута проверяют наличие поля. |
